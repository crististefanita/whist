# Qualification of publication and delivery of results

## Overview

The consumer holds the game records, selection, oracle and external indexation. Generic API or rendering defects follow [routing to the library manager](README.md).

## RPT-OBSERVATION-CONTRACT - validation by declared capabilities

**P2 · adaptor integration.** The explicit profiles already cover neutral reports without HTTP. The combination of an OBSERVE capture with the action and the reported owner shall follow the joint contract; the local feedback shall retain the qualification of the adapter and the data consumed.

- [ ] After delivery of the common capability, qualify the actual adapter and the report produced with the actual consumed library. Check the owner of the capture, inventory expected/actual and refusal to remove the declared capture.

## RPT-BOUNDED-REPORT-HEAP - Safe completion for large suites

**P1 · library owner: HTML publication and verification; consumer: input size.** Passing JUnit tests do not guarantee a canonical report when navigation injection or DOM verification exhausts the heap. Publication failure must preserve test outcomes and must never qualify partial HTML.

- [ ] Measure the peak memory separately for initial rendering, injection of navigation and report verification, depending on the number of comparisons, bodies and inline captures.
- [ ] Avoid repeated full copies of the document at the publication and verification stages; each step shall be capable of processing a large valid report below the declared limit of the heap.
- [ ] Qualify the limits with small, medium and large synthetic reports, including repeated payloads and inline images. Check the identities of Junit-HTML, all mandatory captures and bytes after publication.
- [ ] Upon crossing an explicit limit, issue a localized diagnosis identifying the stage and keeping JUnit's result and available evidence; do not let an exception of heap turn into an ambiguous lack of file.

Both producer and verifier need qualification. Increasing one process's heap limit does not close the criterion or prove that the report is publishable in the standard environment.

## RPT-EXTENT-REPEATED-PAYLOAD - Compaction without audit loss

**P2 · component HTML compaction without reducing evidence.** Identical Payload can increase the size and navigation time of the report. Accurate profiling belongs to the external run dossier; the criterion follows the compaction mechanism and the audit maintenance. Reusable capabilities follow [common routing](README.md#change-ownership).

- [ ] The compact profile must keep each owner, comparison, verdict and fully accessible offline body in the same HTML. Do not remove values or move content to ZIP, JSON or external files.
- [ ] Evaluate internal content-addressed references for repeated byte-identical bodies. Each invocation must expose its complete original content; the content may be stored once in the autonomous HTML.
- [ ] Keep the PNG inline Base64 and navigation to the original checkpoint; the text optimisation shall not alter the identity of the capture or the association of the owner.
- [ ] Expose a size summary by category and a configurable presentation option. The preview may shorten, but the whole body and criterion PASS/FAIL remain verifiable.
- [ ] Qualify HTML alone in an empty directory with repeated, long, different payloads and Base64. Confront byte-for-byte each visible value and check the final report hash.

Measurement justifies investigating the reduction of redundancy; it does not prove that all similar bodies make the same sense. References can be unified only for identical payloads, and the verdict cannot depend on compact mode.
